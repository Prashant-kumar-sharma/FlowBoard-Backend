Section 01

Executive Summary

Traditional task-management platforms often degrade under collaboration-heavy workloads because business logic, data ownership, and notification workflows are tightly coupled. As the number of users, boards, comments, and attachments increases, a monolithic design makes it harder to preserve responsiveness, isolate failures, and secure identity propagation across features.

FlowBoard addresses this by decomposing the domain into independently deployable services for authentication, workspace management, boards, lists, cards, comments, labels, notifications, and payments. The API Gateway centralizes request entry, Eureka enables service discovery, Kafka powers asynchronous notifications, Redis improves hot-path access patterns, and Angular provides a responsive real-time user experience.

The resulting system is architecturally aligned with enterprise SaaS expectations: security boundaries are explicit, cross-cutting concerns are centralized, operational visibility is built into the platform, and service contracts are isolated enough to support incremental scaling and future product expansion.

Business Problem

Collaboration tools frequently struggle with live synchronization, secure multi-user workflows, and clean modularity under growth.

Solution Overview

FlowBoard uses domain-specific microservices with asynchronous eventing and centralized ingress to keep user workflows responsive while preserving bounded contexts.

Core Value Proposition

Secure team collaboration, real-time task movement, operational scalability, and readiness for enterprise deployment patterns such as CI/CD, observability, and horizontal growth.

Enterprise Relevance

The architecture directly demonstrates patterns valued in industry: gateway-based ingress, service discovery, async messaging, zero-session REST APIs, and service-level ownership.

Section 05

Security Architecture

JWT lifecycle: Auth Service issues access and refresh tokens after successful login, OTP verification, or OAuth2 success handling. The gateway validates the token signature and extracts user identifiers and role claims before forwarding requests downstream.

Authentication workflow: Public auth routes are permitted in the Auth Service security chain, while all other requests require authentication. OTP data is hashed with BCrypt, time-bounded, and tracked with attempt counts for rate limiting. OAuth2 is currently wired for Google in code; the same success-handler pattern can be extended to GitHub.

Authorization model: User roles include `MEMBER`, `BOARD_ADMIN`, `PLATFORM_ADMIN`, and `SYSTEM`. Sensitive routes such as `/api/v1/admin/**` require platform-admin authority. The gateway enriches requests with `X-User-Email`, `X-User-Id`, and `X-User-Role` headers so downstream services can authorize without re-parsing tokens.

Inter-service trust: Internal APIs such as `auth/internal` and `payments/internal` support cluster-only communication. In an enterprise production rollout, these should be additionally protected with mTLS, network policies, or signed service credentials to reduce reliance on network location alone.

Security Controls

  • BCrypt password hashing
  • BCrypt OTP hash storage
  • Stateless JWT validation in gateway
  • CORS controls in gateway and services
  • Role-based route restrictions
  • Circuit breakers on routed service calls

Current-state note

Gateway configuration already centralizes auth filtering and header propagation. Redis-backed gateway rate limiting and distributed tracing are recommended hardening additions rather than fully implemented features in the current repo.

Section 06

Database Design

FlowBoard uses a database-per-service strategy at the logical schema level. Confirmed schema names in the codebase include `flowboard_auth`, `flowboard_workspace`, and `flowboard_board`; the same pattern extends to the other services. This reduces coupling, preserves service autonomy, and enables targeted backup, migration, or performance tuning per domain.

Relational storage is appropriate because the platform requires integrity across membership, ordering, ownership, audit events, and payment records. Entity relationships inside a service remain strongly modeled, while cross-service references are stored as foreign-key-like identifiers rather than direct database constraints.

Redis is used as a read-performance layer in multiple services, with a configurable TTL of `10m` visible in workspace and board service properties. This is well suited for board metadata, entitlement status, and list/card lookups that are read frequently but updated less often than rendered.

Transaction boundaries are local to each microservice. Cross-service consistency is achieved through compensating operations, internal cleanup endpoints, and Kafka-backed event publication rather than distributed XA transactions.

Data isolation strategy

  • Each service owns its schema and entity lifecycle.
  • Cross-service joins are avoided at the database level.
  • Identifiers are exchanged over REST or Kafka events.
  • Soft archival is used for some list/card states before deletion.

Redis caching strategy

  • Cache abstraction enabled in board, workspace, list, card, and payment paths.
  • Improves repeated entitlement, board, and task retrieval.
  • TTL-based expiration reduces stale data risk.

Section 08

Event-Driven Architecture

FlowBoard uses Kafka to decouple user-facing workflows from notification delivery and downstream side effects. This allows card assignment, workspace invitations, and payment activation to complete quickly for the initiating user while notifications are processed asynchronously.

Confirmed producer topics in the codebase include `flowboard.card.assigned`, `flowboard.card.moved`, `flowboard.board.member.invited`, `flowboard.workspace.member.invited`, `flowboard.payment.premium.activated`, `flowboard.mention.notification`, and `flowboard.account.status.changed`. Notification service defines additional topics such as overdue and comment topics for future extension.

Retry strategy in the current code relies primarily on Kafka consumer durability and logging on failure. For production hardening, dead-letter topics, retry backoff policies, and idempotency keys should be introduced for side-effect safety at scale.

Section 09

API Gateway Details

The API Gateway is the system ingress controller on port `8080`. It owns central routing, CORS policy, JWT validation, Swagger aggregation, and resilience behavior. Routes use `lb://` URIs, which means concrete instances are resolved dynamically using Eureka service discovery.

Every protected request passes through `AuthenticationFilterGatewayFilterFactory`, which validates the Bearer token and injects identity headers downstream. This is a crucial design choice because it keeps services focused on domain authorization while avoiding repeated JWT parsing logic in every microservice.

Resilience4j circuit breakers are configured per routed service, creating isolated fallback boundaries for auth, workspace, payment, board, list, comment, label, card, and notification flows.

Rate limiting and tracing: these are stated responsibilities of the gateway architecture. The current repo has the right centralization point, but Redis-backed request limiting and distributed tracing should be added to fully satisfy enterprise non-functional requirements.

Current routing groups

  • `/api/v1/auth/**` and `/api/v1/admin/**`
  • `/api/v1/workspaces/**`
  • `/api/v1/boards/**`, `/api/v1/lists/**`, `/api/v1/cards/**`
  • comments, labels, notifications, payments
  • aggregated `/v3/api-docs/*` routes for Swagger UI

Enterprise benefits

  • Single external API surface
  • Central auth enforcement
  • Simplified frontend service discovery
  • Per-service circuit breaker configuration
  • Easy insertion point for tracing and quotas

Section 10

Real-Time Communication

The Angular frontend includes a `WebSocketService` that connects using SockJS to `environment.wsUrl`, currently `http://localhost:8085/ws`, and subscribes to board-scoped topics such as `/topic/board/{boardId}/card-moved` and `/topic/board/{boardId}/comment-added`.

Card, comment, and label services each define STOMP broker configuration with `/topic` and `/queue` destinations and `/app` application prefixes. In practice, the active frontend integration is centered on card-service for board updates, while additional services are positioned for broader real-time usage.

For enterprise scaling, the simple in-memory broker should evolve toward a distributed message broker relay or dedicated WebSocket gateway to support clustered node fan-out and sticky-session-independent event delivery.

Section 12

Detailed Use Case Specifications

Use Case: OTP Registration

Actor: Guest User

Preconditions: Email is not already registered.

Main Flow: Request OTP, receive email, verify OTP, create user, issue JWT pair.

Alternative Flow: OTP expired, attempts exceeded, duplicate email.

Result: User account is created and authenticated.

Use Case: Create Workspace

Actor: Authenticated Member

Preconditions: Valid JWT and plan eligibility.

Main Flow: Gateway validates JWT, workspace service checks entitlement/free limit, persists workspace, emits event.

Alternative Flow: Premium required or membership limits exceeded.

Result: Workspace appears in dashboard and audit log.

Use Case: Create Board and Invite Members

Actor: Board Admin

Preconditions: User belongs to the workspace.

Main Flow: Create board, add members with role, publish board invitation event.

Alternative Flow: Duplicate member or insufficient rights.

Result: Board is provisioned and invite notifications are generated.

Use Case: Move Card in Real Time

Actor: Team Member

Preconditions: User has board access and card exists.

Main Flow: UI sends move request, card service updates ordering, publishes event, STOMP subscribers refresh state.

Alternative Flow: Stale ordering or access denied.

Result: Card appears in the new list for all connected viewers.

Use Case: Premium Checkout

Actor: Member

Preconditions: User is authenticated.

Main Flow: Create Razorpay order, complete payment, confirm payment, activate subscription, publish premium event.

Alternative Flow: Verification failure or duplicate confirmation.

Result: Subscription is activated and user receives confirmation/invoice.

Use Case: Admin Suspension

Actor: Platform Admin

Preconditions: Admin is authenticated with elevated role.

Main Flow: Admin invokes suspend route, auth service updates user state, publishes account-status event, notification service emails user.

Alternative Flow: User not found or invalid role transition.

Result: User access is blocked and audit visibility improves.

Section 13

Exception Handling Strategy

Each service includes a `GlobalExceptionHandler` class to centralize mapping from domain exceptions to HTTP responses. Common exception types visible in the repo include `ResourceNotFoundException`, `UnauthorizedException`, `AccessDeniedException`, `DuplicateResourceException`, `PaymentRequiredException`, and validation-related failures.

Auth Service additionally defines an `ErrorResponse` structure with fields for HTTP status, error name, message, field-level validation errors, and timestamp. This is a sound pattern for consistent frontend error display and should be standardized across all services.

Gateway-level failures are handled separately. Invalid or missing Bearer tokens return JSON `401` responses from the gateway filter before any downstream service receives the request.

Reduces repeated reads for boards, lists, entitlements, and other frequently accessed domain views.

Horizontal Scaling

Stateless services can scale independently behind the gateway; hot paths center on card and notification traffic.

Section 17

Challenges & Solutions

JWT propagation issue

Challenge: downstream services need identity without duplicating token parsing. Solution: gateway validates JWT and injects trusted `X-User-*` headers, creating a clear ingress trust boundary.

Docker networking

Challenge: local hostnames and startup order become brittle in multi-container systems. Solution: Compose network aliases, health checks, and environment-based internal URLs stabilize service communication.

Service discovery

Challenge: static service endpoints reduce deployment flexibility. Solution: Eureka plus `lb://` gateway routing enables dynamic service registration and discovery.

Async consistency

Challenge: notifications should not delay user actions. Solution: event publication decouples side effects, while notification service resolves user/card context asynchronously.

CORS handling

Challenge: frontend and service origins differ in development. Solution: gateway global CORS plus service-level CORS config reduce browser rejection risk, though standardizing all dev traffic through the gateway remains a strong next step.

Notification fan-out

Challenge: a single event may require storage, email, and UI deep linking. Solution: notification service centralizes event enrichment, persistence, and dispatch logic.

Section 22

Conclusion

FlowBoard is a strong demonstration of enterprise application engineering. It combines a modern Angular frontend with a rich Spring Boot microservices backend, layered security controls, real-time collaboration, asynchronous notifications, and payment-aware business rules.

From an academic standpoint, the project shows depth across architecture, coding, DevOps, security, and testing. From an industry standpoint, it mirrors real SaaS concerns such as ingress control, service discovery, bounded contexts, messaging, observability, and horizontal scale.

The most valuable learning outcome is not just that each technology appears in the stack, but that they are composed meaningfully: gateway for trust, Kafka for decoupling, Redis for speed, Docker for reproducibility, and domain services for clarity. That makes FlowBoard a credible portfolio project, a strong final-year review submission, and a compelling interview discussion piece.
